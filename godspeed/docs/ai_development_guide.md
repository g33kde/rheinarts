# AI Development Guide

## Purpose

This document defines how AI coding agents should contribute to the **Godspeed** project.

The goal is to make AI a productive team member while ensuring the codebase remains maintainable, consistent, and enjoyable to work on.

This document is the primary reference for any AI agent (ChatGPT, Codex, Cursor, Claude Code, GitHub Copilot, etc.) before generating code.

---

# Project Vision

Godspeed is a browser-first cooperative roguelite maze shooter where players descend through ancient techno-divine labyrinths, fighting intelligent guardians while the maze itself evolves.

Everything generated by AI should reinforce this vision.

If a requested feature conflicts with the vision, the AI should explain why and suggest alternatives.

---

# Design Principles

The game should always prioritize:

* Fast arcade gameplay
* Simple controls
* High replayability
* Procedural exploration
* Skill-based combat
* Cooperative gameplay (future)
* Strong atmosphere
* Clean architecture

Do not introduce unnecessary complexity.

# Coding Principles

Generated code should be:

* Readable
* Modular
* Strongly typed
* Well documented
* Easy to test

Avoid clever solutions.

Prefer obvious solutions.

Functions should generally have one responsibility.

---

# Architecture

Use a modular architecture.

Example:

```
game/
    core/
    scenes/
    entities/
    components/
    systems/
    ai/
    ui/
    assets/
    config/
    utilities/
```

Game logic should not be tightly coupled to rendering.

Configuration should live outside gameplay code whenever practical.

---

# File Size

Prefer:

* Files under 300 lines
* Classes under 200 lines
* Small focused functions

Split code before it becomes difficult to navigate.

---

# AI Responsibilities

AI is expected to:

* Generate production-quality code
* Write tests
* Update documentation
* Refactor safely
* Improve readability
* Explain architectural decisions
* Identify technical debt
* Suggest improvements

AI should never silently change gameplay behavior.

---

# Documentation Rule

Whenever a significant feature is added:

Update the appropriate documentation inside `docs/`.

Examples:

* gameplay.md
* enemy_design.md
* progression.md
* technical_design.md
* roadmap.md

Documentation is part of the definition of done.

---

# Testing

Every gameplay feature should include appropriate tests where feasible.

Prefer testing:

* Game rules
* State transitions
* Enemy behaviour
* Upgrade logic
* Save/load
* Procedural generation

Avoid brittle tests tied to rendering details.

---

# Gameplay Philosophy

Gameplay comes before graphics.

If forced to choose between:

* Better mechanics
* Better visuals

Choose better mechanics.

---

# Performance

The game targets smooth browser play.

AI should:

* Minimize allocations in the main update loop
* Avoid unnecessary object creation
* Use pooling where appropriate
* Profile before optimizing
* Keep frame time predictable

---

# Assets

During development AI may generate:

* Placeholder sprites
* Temporary sounds
* Placeholder UI
* Test maps

Production assets may replace these later.

Do not tightly couple gameplay to placeholder assets.

---

# Git Workflow

Use feature branches.

Keep `main` deployable.

Recommended commit style:

```
feat:
fix:
refactor:
docs:
test:
build:
ci:
perf:
```

Small focused commits are preferred.

---

# Pull Requests

Every pull request should include:

* Summary
* Motivation
* Technical approach
* Testing performed
* Documentation updated

---

# AI Prompting

When implementing a feature, AI should first:

1. Read the relevant documents in `docs/`
2. Explain the implementation plan
3. Identify risks or trade-offs
4. Implement in small steps
5. Update documentation

Avoid generating large, monolithic code drops.

---

# Game Feel

Every gameplay decision should reinforce:

* Fast
* Responsive
* Fair
* Tense
* Rewarding

The player should always feel in control.

---

# Visual Direction

Maintain the project's identity.

Ancient divine technology blended with science fiction.

Key visual motifs:

* Monolithic stone
* Floating geometry
* Glowing runes
* Gold and obsidian
* Celestial lighting
* Sacred machinery

Never drift toward generic medieval fantasy or generic cyberpunk.

---

# Audio Direction

Music should combine:

* Sacred choirs
* Dark ambient textures
* Ominous synthesizers
* Mechanical resonance

Silence should be used intentionally.

---

# Scope Control

Version 1.0 includes:

* Browser support
* Single player
* Full-maze camera
* Top-down gameplay
* Three biomes
* Five enemy types
* One boss
* Permanent unlocks
* Run-based upgrades

Do not expand scope without documenting the proposal first.

---

# Decision Making

When multiple solutions exist:

1. Simpler
2. More maintainable
3. Easier to test
4. Better documented
5. Better gameplay

Only optimize after correctness and clarity.

---

# Definition of Done

A feature is complete when:

* Code builds successfully
* Tests pass
* Documentation is updated
* Linting passes
* No obvious regressions exist
* Gameplay has been manually verified

---

# Guiding Principle

AI should behave like a senior game developer joining an established project—not like an autocomplete engine.

Its responsibility is not only to write code, but to preserve the long-term quality, vision, and maintainability of **Godspeed**.
